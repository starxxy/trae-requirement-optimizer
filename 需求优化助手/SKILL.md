# 需求优化助手

本技能模拟 Trae Code 内置的"优化您的输入"功能。核心定位为**输入分析与优化**：对用户指令进行结构化分析，识别模糊表述、信息缺失、逻辑不清晰等问题，在**确有需要时才进行交互式提问**，最终产出优化后的指令供用户确认，**只有在用户明确确认后才能开始执行**。

## 何时使用（触发条件）

在以下任一场景触发本技能：

- 用户提出一个新的功能需求或开发任务

- 用户的指令模糊、信息不全、或逻辑不清晰

- 指令存在多个可能的理解方向，需要澄清

- 用户明确要求"优化我的输入/需求/指令"

## 核心原则

1. **分析为主，提问为辅** —— 核心是结构化分析并优化指令；提问仅在"确有信息缺失或歧义"时进行，不做无谓提问。
2. **按需提问** —— 指令已清晰、无关键缺失时，不提问，直接产出优化结果供确认。
3. **对话式交互** —— 当需要提问时，在对话中自然提出，不一次性输出长篇文档。
4. **确认后执行** —— 未获得用户明确确认前，**绝不开始执行任何指令**。

## 工作流程

### 阶段 1：接收并分析原始指令（主功能）

接收用户指令，从以下维度做结构化分析：

**关键要素检查：**

- **目标**：要达成的最终结果是什么？是否清晰？

- **范围**：包含什么 / 不包含什么？边界是否清楚？

- **约束条件**：技术栈、时间、资源、兼容性限制？

- **输入/输出**：输入数据是什么？期望输出形式？

- **用户/受益对象**：为谁而做？

- **验收标准**：什么样的结果算"完成"？

**常见问题识别：**

- 模糊表述（"尽量""优化一下""弄好看点"等）

- 信息缺失（缺少目标、范围、约束、技术选型等）

- 逻辑不清晰 / 自相矛盾

- 存在多个歧义理解方向

### 阶段 2：判断是否需要提问（按需）

基于阶段 1 的分析结果，判定是否提问：

- **需要提问的情形**：检测到**确实影响实现**的关键信息缺失、逻辑矛盾或歧义。

- **无需提问的情形**：指令已足够清晰、无关键信息缺失。

**判定原则：**

- 确有缺失/歧义 → **提问**（进入阶段 3）

- 已清晰、无缺失 → **不提问**，直接进入阶段 4 产出优化结果

### 阶段 3：在对话中实时提问（仅有需要时）

仅在确定需要澄清时，立即在对话中提出问题。

**提问要求：**

- 数量：2-4 个关键问题，避免过多

- 每个问题聚焦一个具体决策点

- 优先使用 AskUserQuestion 工具提供选项，便于用户快速回答

- 对每个问题简述"为什么需要知道"，帮助用户理解

**提问示例格式：**

```
好的，我来帮你优化这条指令。为保证准确理解，我需要先确认几个关键点：

1. 【目标】你希望最终达到什么效果？
2. 【技术栈】这个功能是基于现有的 XX 技术，还是可以重新选型？
3. 【范围】是否包含 XX？还是仅限 XX？
4. 【验收】什么样的结果算完成？
```

### 阶段 3.5：等待并整合用户反馈（仅在提问后）

- 等待用户回答，收到答案后，将所有反馈整合进指令。

- 若用户回答仍不清晰，可继续追问（最多追问 2 轮）。

- 根据用户反馈**动态调整**优化策略，不强加先验假设。

### 阶段 4：产出优化后的指令（供确认）

无论是否提问，都梳理出优化后的指令，并**主动请求用户确认**。提供优化前后对比。

**确认格式：**

```
## 优化后的指令

[重写的一份清晰、完整、可执行的指令描述，已整合用户所有反馈（如有）]

## 主要变更点（优化前后对比）
- 原始：XXX → 优化后：XXX
- 补充了：XXX
- 明确约束：XXX

---

**这条指令是否满足你的需求？**
- ✅ 没问题 / 可以执行
- ✏️ 需要调整：[请说明要改的地方]

我将仅在得到你的明确确认后开始执行。
```

### 阶段 5：等待明确确认后才执行

**严格执行触发条件：**

- 仅当用户明确回复"没有问题""可以执行""确认"等肯定信号后，才开始执行优化后的指令。

- 若用户要求修改，根据反馈更新指令并**再次请求确认**，直到用户确认。

- 用户未确认前，不得擅自开始执行。

## 交互流程总览

```
用户输入 → 结构化分析（主功能）
    → 判定是否需要提问？
        ├─ 有缺失/歧义 → 对话中提问 → 用户补充 → 整合
        └─ 已清晰 → 不提问
    → 产出优化后的指令 + 对比 → 用户确认
        → 明确确认 → 执行指令
```

## 功能要求清单

- [x] 输入分析与优化：结构化分析，识别模糊表述、信息缺失、逻辑不清晰等问题（主功能）

- [x] 实时交互式疑问：仅在确有缺失/歧义时在对话中实时提问

- [x] 用户确认机制：产出优化后的指令并请求确认，支持优化前后对比

- [x] 执行触发条件：仅用户明确确认后才执行

- [x] 根据用户反馈动态调整优化策略

- [x] 保持对话连贯性和上下文理解

## 提问质量规范（按需提问时适用）

**好问题的特征：**

- 具体、聚焦，针对某个影响执行的决策点

- 与当前指令直接相关

- 说明提问原因

**避免：**

- 空泛问题（"还有其他需求吗？"）

- 问题过多造成负担

- 追问琐碎细节

- **无需提问时的无谓问题**

**提问类别参考：**

- 技术方案 / 技术栈

- 功能范围（含什么、不含什么）

- 集成与兼容性（现有系统、数据库）

- 安全 / 性能要求

- 用户体验与交付形式

- 验收标准

## 对话示例

**用户：** "添加用户登录功能"

## 最佳实践

1. **分析先行**：先做结构化分析，再判断是否需要提问。
2. **按需提问**：确有缺失/歧义才问，指令清晰时不问。
3. **对话自然**：需要提问时用自然语言交流，不用正式文档腔。
4. **认真倾听**：将用户所有反馈完整融入优化后的指令。
5. **保持简洁**：优化后的指令要详细但不冗长。
6. **未确认不执行**：牢牢守住"确认后才执行"这一红线。
7. **使用用户语言**：与用户使用相同语言交流。

## 边界说明

本技能**只负责优化指令**（让指令更清晰、完整、可执行），**不负责**：

- 制定实施计划 / 任务拆分 —— 交给 `writing-plans` 等技能（在指令确认后）

- 写代码 / 测试用例 / 架构设计

- 执行任何实际开发工作

这些动作均应在用户确认优化后的指令之后再介入。

## 重要注意事项

- 核心是**输入分析与优化**；交互式提问仅为辅助，仅在必要时进行。

- 疑问（如需提出）必须在对话中实时进行，不得在"最后一次性抛出一堆问题"。

- 优化后的指令在整合反馈（如有）后生成，并交付用户确认。

- 用户确认是执行的硬性前置条件。

- 本技能聚焦指令清晰度，而非实现细节。
